Kubernetes에 애플리케이션을 올리는 것과 안정적으로 운영하는 것은 다른 문제다. Pod가 `Running`이어도 사용자의 요청에 답하지 못할 수 있고, 응답이 느려지는 원인을 알 수 없을 수도 있다.

## 세 개의 입구

블로그 컨테이너에는 처음부터 다음 엔드포인트를 둔다.

| 경로 | 역할 |
| --- | --- |
| `/health/live` | 프로세스가 살아 있는지 확인한다. |
| `/health/ready` | 현재 요청을 받을 준비가 됐는지 확인한다. |
| `/metrics` | Prometheus 형식의 런타임 지표를 노출한다. |

liveness는 재시작 판단에, readiness는 트래픽 전달 판단에 사용한다. 둘을 하나의 체크로 합치면 외부 의존성의 짧은 장애가 불필요한 재시작으로 이어질 수 있다.

## 지표는 플랫폼이 수집한다

애플리케이션은 지표를 노출할 뿐 저장하거나 시각화하지 않는다. ServiceMonitor가 대상을 발견하고 Prometheus가 수집하며 Grafana가 보여 준다.

```text
blog Pod /metrics
  -> ServiceMonitor
  -> Prometheus
  -> Grafana dashboard
```

이 분리를 지키면 애플리케이션 이미지는 특정 Prometheus 주소를 몰라도 되고, 관측 환경을 바꾸더라도 앱 코드를 수정할 필요가 없다.
