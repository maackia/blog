처음 저장소에는 React와 Vite로 만든 화면 몇 개가 전부였다. 화면을 더 만드는 일은 어렵지 않았지만, 이 블로그를 Kubernetes에 올리고 직접 운영하려면 **애플리케이션의 경계**부터 다시 정할 필요가 있었다.

## 블로그도 하나의 운영 대상이다

이번 기반에서 블로그는 단순한 정적 화면이 아니다. 다음 계약을 가진 독립적인 애플리케이션이다.

- 글은 저장소 안의 MDX 파일로 관리한다.
- 각 글은 빌드 시점에 정적 HTML로 생성한다.
- 컨테이너는 liveness와 readiness 엔드포인트를 제공한다.
- Prometheus가 수집할 수 있는 `/metrics` 엔드포인트를 제공한다.
- 이미지는 GHCR에 변경 불가능한 태그로 게시한다.

이 계약이 있으면 플랫폼 저장소는 애플리케이션 내부를 알 필요가 없다. 어떤 포트로 실행되는지, 상태를 어디서 확인하는지, 어떤 이미지를 배포할지만 알면 된다.

## 애플리케이션과 플랫폼을 분리했다

`blog` 저장소는 코드와 컨테이너 이미지를 책임진다. `container-platform-lab` 저장소는 Kubernetes 리소스와 관측 환경을 책임진다.

```text
blog source
  -> GitHub Actions
  -> GHCR image
  -> Kubernetes Deployment
  -> ServiceMonitor
  -> Prometheus
  -> Grafana
```

앞으로 마인크래프트 서버 같은 전혀 다른 워크로드를 추가하더라도 같은 플랫폼 규칙을 재사용할 수 있다.

## 먼저 얇게 끝까지 연결한다

블로그 기능을 전부 완성한 뒤 처음 배포하지 않기로 했다. 글 한 편, 컨테이너 하나, 대시보드 하나를 먼저 끝까지 연결한다. 검색이나 댓글 같은 기능은 그 흐름이 안정된 뒤 추가한다.

작은 수직 슬라이스를 먼저 완성하면 애플리케이션 개발과 Kubernetes 실습이 서로 기다리지 않는다. 지금의 목표는 기능이 많은 블로그가 아니라, **계속 운영하며 확장할 수 있는 블로그**다.
